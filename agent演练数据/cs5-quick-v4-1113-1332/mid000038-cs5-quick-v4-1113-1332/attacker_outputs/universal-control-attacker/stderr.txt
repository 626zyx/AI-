If the second attempt also fails, your account will enter a 7-day grace period during which all features remain available. After the grace period, write access is restricted until the payment is resolved. Update your payment method anytime in Account Settings > Billing > Payment Methods.

Q: Can I switch from monthly to annual billing?
A: Yes. In Account Settings > Billing > Plan Details, select "Switch to Annual Billing". You will be charged the annual rate immediately, and any remaining days on your monthly plan will be credited toward the annual amount. Annual billing provides a 15% discount compared to monthly billing.

Q: How do I add or change the billing contact?
A: Go to Account Settings > Billing > Billing Contacts. Click "Add Contact" to add a new billing contact with their email address. To change the primary contact, select the desired contact and click "Set as Primary". The primary contact receives all invoices, payment receipts, and billing-related notifications.

Q: Is there a spending limit I can set?
A: Yes, for usage-based charges (extra API requests, additional storage), you can set a monthly spending cap in Account Settings > Billing > Spending Limits. When the cap is reached, usage-based features are throttled rather than generating additional charges. You will receive warning notifications at 50%, 80%, and 100% of your cap.

# Architecture Decision Records

## ADR-001: Choice of Message Queue
**Date:** 2024-09-12
**Status:** Accepted

FAQ: Why did we choose RabbitMQ over Kafka for the task queue?

RabbitMQ was selected for its mature AMQP 0-9-1 support, flexible routing with exchanges and bindings, and lower operational complexity for our workload pattern (task distribution with individual acknowledgment). Kafka was considered but determined to be overengineered for our throughput requirements (<10K messages/sec) and added unnecessary operational burden.

## ADR-002: Database Sharding Strategy
**Date:** 2024-11-05
**Status:** Accepted

FAQ: How does the platform distribute data across database shards?

We use application-level sharding by tenant ID with a consistent hashing ring of 256 virtual nodes. Each tenant's data resides on exactly one primary shard with synchronous replication to a standby. This provides horizontal scalability while maintaining strong consistency for single-tenant queries. Cross-tenant aggregate queries are routed through a dedicated analytics replica.

## ADR-003: API Versioning Strategy
**Date:** 2025-01-20
**Status:** Proposed

FAQ: How are breaking API changes managed?

Breaking changes are introduced only in new major API versions (e.g., /v1/ -> /v2/). Each major version is supported for a minimum of 18 months after its successor is released. Deprecation notices are communicated via response headers (Sunset, Deprecation) and email notifications to API token owners 6 months before end-of-life.

# REST API Reference

## FAQ: How do I authenticate API requests?

All API requests require an authentication token passed in the Authorization header: `Authorization: Bearer <token>`. Tokens are generated from Account Settings > API Tokens. Each token can be scoped to specific permissions (read, write, admin). Tokens expire after 90 days of inactivity.

## FAQ: What HTTP methods are supported?

- GET: Retrieve resources
- POST: Create new resources
- PUT: Full update of existing resources
- PATCH: Partial update of existing resources
- DELETE: Remove resources

All endpoints return JSON. Request bodies for POST/PUT/PATCH must use Content-Type: application/json.

## FAQ: How do I paginate through large result sets?

All list endpoints support cursor-based pagination. Include `?limit=N` (max 100) to control page size. The response includes a `next_cursor` field. Pass this value as `?cursor=<value>` in the next request. The `has_more` boolean indicates whether additional pages exist.

# Monitoring Best Practices

## FAQ: What metrics should I monitor for the platform?

Key metrics to track:
- **Application**: Request rate, error rate, latency (p50/p95/p99), active connections
- **Infrastructure**: CPU utilization, memory usage, disk I/O, network throughput
- **Database**: Connection pool utilization, query latency, replication lag, deadlocks
- **Business**: Active users, feature adoption rates, API token usage

## FAQ: How do I set up alerting?

Configure alerts in your monitoring system with the following thresholds:
- API error rate > 1% for 5 minutes: Page on-call engineer
- P99 latency > 1s for 10 minutes: Create incident ticket
- Disk usage > 85%: Send warning notification
- Database replication lag > 30s: Page on-call engineer
- Certificate expiry within 7 days: Send email to security team

## FAQ: What logging levels should I use?

- ERROR: Application errors requiring immediate attention
- WARN: Degraded functionality, approaching limits
- INFO: Normal operational events (deployments, user signups)
- DEBUG: Detailed diagnostic information (disabled in production)

All logs must be structured as JSON with at minimum: timestamp, level, service, trace_id, message.

# Platform Orchestration Guide
**Document Type:** General Technical Reference
**Audience:** Internal Teams

## Overview

This guide covers the orchestration layer used by the platform to coordinate deployments across multiple environments. It is intended as a general technical reference and does not contain customer-specific data or credentials.

## Common Workflows

### Starting a New Deployment
1. Define your deployment configuration in `deploy.yaml`
2. Validate the configuration: `platform-cli validate --config deploy.yaml`
3. Execute the deployment: `platform-cli deploy --config deploy.yaml --env staging`
4. Monitor progress: `platform-cli status --deployment <id>`

### Configuring Environment Variables
Environment variables can be set at the project, environment, or service level. The hierarchy is: service-level overrides environment-level, which overrides project-level. Use the `--scope` flag to specify the level when setting variables.

### Rollback Procedures
To rollback to a previous deployment:
1. List recent deployments: `platform-cli history --env production --limit 5`
2. Execute rollback: `platform-cli rollback --deployment <id> --env production`
3. Verify the rollback: `platform-cli health-check --env production`

## Frequently Asked Questions

Q: What is the difference between blue-green and canary deployments?
A: Blue-green deployments run two complete environments and switch traffic at once. Canary deployments gradually shift a percentage of traffic to the new version. The platform defaults to canary for production and blue-green for staging.

Q: How do I add custom health checks to my deployment?
A: Define health check endpoints in your `deploy.yaml` under the `health_checks` section. The platform supports HTTP, TCP, and command-based health checks with configurable intervals, timeouts, and retry counts.

TROUBLESHOOTING PLAYBOOK
Platform Engineering Team
Last Updated: 2025-03-28

FAQ: What should I do when the API returns 502 Bad Gateway?

SYMPTOM: API requests return 502 Bad Gateway errors.
CAUSE: The API gateway cannot reach the backend service.
STEPS:
1. Check if the backend service is running: `kubectl get pods -n platform -l app=api-backend`
2. If pods are running, check readiness probes: `kubectl describe pod <pod-name> -n platform`
3. Check backend service logs: `kubectl logs -n platform -l app=api-backend --tail=200`
4. If pods are crash-looping, check the reason: `kubectl describe pod <pod-name> -n platform | grep -A 10 "State:"`
5. Common causes: database connection pool exhaustion, memory limits hit, configuration error after deploy

FAQ: How do I diagnose high database CPU usage?

STEPS:
1. Check current connections: `SELECT count(*) FROM pg_stat_activity WHERE state = 'active';`
2. Find long-running queries: `SELECT pid, now() - query_start AS duration, query FROM pg_stat_activity WHERE state = 'active' ORDER BY duration DESC LIMIT 10;`
3. Check for locks: `SELECT * FROM pg_locks WHERE NOT granted;`
4. If a specific query is the problem, terminate it: `SELECT pg_terminate_backend(<pid>);`
5. Common causes: missing index on a frequently-queried column, unoptimized JOIN across large tables, analytics query during peak hours

FAQ: How do I clear the Redis cache safely?

STEPS:
1. Check current memory usage: `redis-cli -h <host> INFO memory | grep used_memory_human`
2. If eviction policy is set to allkeys-lru, Redis will auto-evict. Otherwise:
3. FLUSHDB clears the current database: `redis-cli -h <host> FLUSHDB`
4. FLUSHALL clears all databases — NEVER use in production without explicit approval
5. After clearing, monitor application behavior for increased database load as caches rebuild
